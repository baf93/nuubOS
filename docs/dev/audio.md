# Product Audio

## Target architecture (§23)
Standard Linux audio: PipeWire + minimal headless WirePlumber; `nuubos-audio-service` (audiod) is the sole Product API/policy owner. One graph for Speaker, Headphones, HDMI, Bluetooth, System Sounds, Home Music, Test Sound and application streams; ALSA `default` and native PipeWire clients work without nuubOS-specific knowledge. The custom `dmix` production path goes away in the final architecture. Migrate capability by capability; BlueALSA may stay temporarily to keep qualified Bluetooth while moving to native BlueZ via WirePlumber; never delete a working transitional backend before its replacement is qualified.
- §23.1 Qualify PipeWire/WirePlumber on H700 against the previous ALSA/BlueALSA path: idle CPU/wakeups, RAM, playback CPU, xrun/underrun, latency/responsiveness, Bluetooth, suspend/resume, stability. Disproportionate overhead → evaluate a smaller nuubOS proxy/router before freezing.
- §23.2 Automatic output priority: Bluetooth > USB > headphone jack > HDMI > internal speaker. Respect physical speaker/jack routing constraints (don't pretend software controls hardware it can't). HDMI media volume belongs to the TV/receiver: no fake adjustable HDMI master.
- §23.3 All product streams (incl. Home Music, System Sounds) mix in the same graph, Bluetooth included; short cues never truncated; Test Sound/System Sounds/Home Music follow an output change while playing.
- §23.4 Volumes: Applications 0–100 (global gain of app streams), System Sounds 0–100 (default 60%), Home Music 0–100, physical-output master where meaningful; 0% = hard mute. Toggles: Navigation Sounds (Navigation, Select, Back, Quick Menu/Settings cues) and Power Sounds (Boot, Restart, Power Off). No separate Startup Sound volume: power cues use the System Sounds volume and are not scheduled when Power Sounds is Off.
- Bluetooth (§25): Beats Studio 3 A2DP was qualified via BlueALSA (44.1 kHz, fixed-format ALSA PCM conversion) — transitional context, inspect current code before changing.

## USB audio (GitHub #9, 2026-10-30)
- Class-compliant digital USB headsets, DACs and microphones use the existing USB host/OTG path. H700 already enables MUSB dual-role and EHCI/OHCI; this change enables `CONFIG_SND_USB_AUDIO=m` with HWDEP/RAWMIDI dependencies. eudev loads the driver by USB modalias. Use the data/OTG port and a host adapter where the board requires one. Passive USB-C analog adapters are outside this driver path. Per-board port/power qualification remains required by EPIC-024.
- `audiod` owns playback policy (`audio-policy.h`): automatic Bluetooth > USB > jack > HDMI > speaker; cast audio still overrides all routes. Explicit `usb` mode persists while unplugged, uses the normal fallback, and returns to USB on reconnect. Explicit analog/HDMI modes keep their existing behavior. USB has its own master/mute, default 50%, persisted as `AUDIO_VOLUME_USB`; reset restores 50%.
- The existing PipeWire registry listener tracks every sink and USB capture source, including devices present when the service starts. No polling. USB nodes use WirePlumber's `alsa_output.usb-*` / `alsa_input.usb-*` names. Availability survives removal of one of multiple devices; losing the selected sink invalidates its id even when another USB sink keeps the logical route `usb`. A capture-only microphone never becomes a playback output. Route classification checks USB before descriptions such as "Analog"; analog selection no longer falls back to an unknown/USB sink. Boot amplifier parking uses the ALSA card id `Codec`, not index 0.
- WirePlumber's ALSA monitor exposes USB playback/capture using its normal card profiles. USB input nodes have `priority.session=2500`, so the default capture source is the real USB microphone rather than a sink monitor or Bluetooth hands-free input. Capture is independent of playback selection; ordinary native PipeWire clients and ALSA clients opening `default` can record without a nuubOS-specific input API. No microphone is inferred from playback availability.
- Socket additions: `OUTPUT SET usb`, `VOLUME GET|SET usb`, `available.usb`, `capture.available.usb`, `volume.usb` in STATUS. D-Bus `GetSnapshot2` / `StateChanged2` append two booleans (USB playback, USB capture) to the original tuple. `GetSnapshot` / `StateChanged` retain their original signatures for existing clients. Home uses the extended contract; Quick Menu and web use the socket snapshot. All output selectors expose USB Audio when a playback sink exists (string 1476, all 29 catalogs).
- Host regression: `python3 package/nuubos/nuubos-audio/tests/usb-audio.py` (cc, pkg-config, ALSA/D-Bus/PipeWire development headers). Compiles the actual daemon translation unit with `-Wall -Wextra -Werror`, fake wpctl and temporary config files. Covers output priority/explicit modes, capture-only and multiple USB devices, unplug/replug and selected sink replacement, no playback gain rewrite on capture events, volume/mute/persistence, and both D-Bus signatures. `AUDIO_TEST_CFLAGS` / `AUDIO_TEST_LIBS` can point at separately extracted host development headers/libraries. Passed normally and with AddressSanitizer/UndefinedBehaviorSanitizer. The WirePlumber fragment parses with `spa-json-dump`; shell/JS syntax and all catalogs pass local checks.
- **Hardware test, 2026-11-05:** on an RG40XX-H with an inexpensive QKZ USB DAC and Tangzu Wagner 2 Red Lion IEMs (names as reported), the DAC reports USB ID `06cb:1594` and product `USB 384KZ HIFI Audio`. ALSA exposes playback and capture, `audiod` selects USB and reports both available, and PipeWire selects the USB sink and source. A low-volume tone and an eight-second capture completed; the user confirmed hearing the tone and intelligible microphone audio. The capture contained 384,000 samples with peak 1715/32768 and RMS 109.1. The branch's kernel, modules and audio/UI components were deployed over Tailscale; the console booted, `audiod` and UI started, and `snd-usb-audio` loaded. Simultaneous playback and capture remain unverified.
- **Qualification pending:** the remaining scenarios below, UI screenshots, and other H700 boards/accessories have not been qualified. Do not mark EPIC-024 USB audio fully qualified from this single-device test.

### Build/deploy and hardware checks still required
Use the existing Docker build workspace and `scripts/compile.sh`, never start a fresh build for this change. For an existing kernel build, enable `SND_USB`, `SND_USB_AUDIO`, `SND_HWDEP` and `SND_RAWMIDI` in its effective `.config` too (the custom config file is applied during kernel configuration, not automatically by a package rebuild). Rebuild `linux`, `nuubos-audio`, `nuubos-localization`, `nuubui-home`, `nuubos-quick-menu` and `nuubos-remote` incrementally. Deploy the kernel Image and its new audio modules/dependencies with regenerated `modules.*`, the audio binaries/helpers, WirePlumber fragment, UI binaries, catalogs and remote admin files using the procedure in build-deploy.md. Restart PipeWire, audiod, remote admin and UI; kernel/module changes may require a reboot.

On each supported board, check cold boot with a headset attached and hotplug after boot. `aplay -l` and `arecord -l` must list the USB endpoints; `nuubos-audioctl status` must show the playback and capture flags independently. Use `XDG_RUNTIME_DIR=/run/nuubos/pipewire wpctl status -n` to verify the default USB source. Record and replay a short clip with `arecord -D default -f S16_LE -r 48000 -c 1 -d 5 /tmp/usb-mic.wav` and `aplay -D default /tmp/usb-mic.wav`; verify simultaneous playback and capture in the requesting app. Check volume 0/unmute, route selection from Home/Quick Menu/web, unplug during playback/capture, reconnect, restart with saved USB mode/volume, reset defaults, and USB microphone-only operation while playback stays on the selected output. With a hub, remove the selected one of two USB outputs and check the remaining sink receives the USB master. Recheck Bluetooth precedence, jack/HDMI fallback and suspend/resume without pops, crashes or a stale route. Record the actual accessory and board tested before claiming support.

## Audio mechanics (§37.5)
- `nuubos-audiod` owns policy; players are child processes (`nuubos-audio-wav-player`, `nuubos-audio-mp3-player`). System sounds use ONE persistent `nuubos-audio-wav-player … sfx-server -` (started on the first cue, commands `PLAY <vol> <path>` on its stdin pipe, a new cue interrupts the current one, restarted on reroute/mute): a player per cue made WirePlumber set up and link a new stream node every time (~60 ms WirePlumber CPU per navigation cue, ~20% of a core while navigating). Between cues the PCM is dropped/prepared = inactive stream, 0 wakeups. Never use `snd_pcm_drain` on the PipeWire ALSA plugin in a long-lived player (it keeps the stream and thread waking) and never wait for `snd_pcm_delay` to reach 0 (it includes graph latency): read the delay once, wait, `snd_pcm_drop`. Home Music volume changes are sent live over a stdin pipe to the running MP3 player (gain ramp per block); never restart the stream for a volume step.
- Master volume ticks are coalesced and applied via `wpctl` once the burst settles.
- The analog sink `nuubos_analog` is a static PipeWire adapter (`91-nuubos-analog-sink.conf`) with `session.suspend-timeout-seconds = 0`: an idle open PCM costs 0 wakeups; suspending it caused first-cue delay + pop.
- Volume Button Step (GitHub #6, 2026-10-29): audiod `volume_step` (`AUDIO_VOLUME_STEP=1|2|5|10` in nuubos.conf, default 1), socket `VOLUME STEP GET` / `VOLUME STEP SET n`, status line `volume.step=`; `VOLUME KEY UP|DOWN` (the Quick Menu's Vol+/Vol-, `nuubos-audioctl volume-key up|down`) moves one step and lands on a multiple of it (73 % + 5 = 75 %, 73 % - 5 = 70 %), replies the STATUS snapshot like `VOLUME ADJUST`. The Quick Menu and Settings volume sliders keep 1 % steps. Settings → Display & Audio: row "Volume Button Step" (1418) after Volume (`DaRow::VolumeStep`, `da-sounds-start` 8, `da-cast-start` 12), confirm opens the choice sheet 1/2/5/10 % like every multiple-choice row (user 2026-10-29); web: same row with a picker (`audio.step`). Checked on the CubeXX through the socket: step 5, 8 % -> up 10 -> down 5 -> down 0; invalid step refused. ui-shot `display_audio_volume_step`.
- Home Music On/Off (user request 2026-10-28, "environments that need silence"): audiod `home_music_enabled` (`AUDIO_HOME_MUSIC_ENABLED=0|1` in nuubos.conf, default 1), socket `MUSIC ENABLED GET` / `MUSIC ENABLED SET 0|1`, status line `home_music.enabled=`. Every start path uses `music_audible()` (enabled and volume > 0): Off stops the player at once and keeps Home's request, so On resumes while Home is in front; a volume change while Off does not start it; the volume is never touched. Settings → Display & Audio: row "Home Music" (139) is the toggle, the slider below is "Music Volume" (1116, dimmed and inert while Off); the AUDIO section has one row more (`da-sounds-start` 7, `da-cast-start` 11, `DaRow::HomeMusicOn`). Web: same toggle (`audio.musicon`) above the Music Volume slider. Checked on the CubeXX through the socket: on -> playing 1, off -> 0, off + volume change -> 0, on -> 1. The old hidden way (confirm on the slider = mute) still works while On.
- Default Home Music: package `nuubos-home-music` downloads 8 Kevin MacLeod (incompetech.com) tracks, CC BY 4.0, unmodified, sha256-pinned, into `/usr/share/nuubos/home-music` with ATTRIBUTION.txt. `audiod` uses them only when the active user's `music` folder has no MP3. Skip Track (`MUSIC NEXT`) is fire-and-forget from the Quick Menu (a slow switch must not close it).
- PipeWire env on target: `XDG_RUNTIME_DIR=/run/nuubos/pipewire` for `pw-cli`/`pw-dump`/`wpctl`.
- Route apply: `reconcile_selection()` runs `nuubos-pw-route` + master volume only when the selected route differs from `applied_route` (last successful apply). BlueZ reports a device connected before WirePlumber creates its sink, so audiod keeps a libpipewire registry listener (`sink_watch`, fd in the main poll, 0 idle wakeups) and retries the apply when a new `Audio/Sink` global appears. Never re-apply on unrelated Bluetooth events: it overwrote the headset's own volume.
- Master volume targets the sink id printed by `nuubos-pw-route select` (`state->sink_id`), never `@DEFAULT_AUDIO_SINK@` right after a route apply: `wpctl set-default` is asynchronous, and on first boot (no WirePlumber state) the default was not resolved yet, so the stored/default master was silently not applied until the user changed the volume. A route counts as applied only once its master volume is set too.
- Bluetooth AVRCP absolute volume: headset buttons change `org.bluez.MediaTransport1.Volume` (0..127); audiod adopts it as the Bluetooth master (`round(v*100/127)`, persisted, no sink write) once the route is applied and no own write is pending, then pushes `volume origin=device output=… volume=…` to `SUBSCRIBE` clients on `audiod.sock` (max 4). The Quick Menu subscribes and shows the volume OSD. The Beats headset sends no AVRCP passthrough keys.
- HFP needs `CONFIG_BT_RFCOMM=m` (autoloaded as `bt-proto-3`); PipeWire's native backend then registers HFP AG/HF and reads headset battery from `AT+IPHONEACCEV`/HF indicators into `org.bluez.Battery1`. Beats Studio³ open HFP (`AT+BRSF=155`, no HF indicators, no `AT+XAPL`) but report battery only over Apple's proprietary AAP: no battery for them on Linux.
## Mute, sound set v5, cues (user requests 2026-10-10)
- Mute: D-Bus `ToggleMute` (audiod) = the hard-mute 0% master of the selected route; unmute restores the level it had (per route, runtime only; a route left at 0% after a restart unmutes to its default). Settings → Display & Audio: confirm on Volume toggles it; the value shows "Muted" at 0%. The QM Audio row is unchanged (confirm = outputs). Applications and Home Music mute the same way (socket `APPLICATIONS MUTE TOGGLE` / `MUSIC MUTE TOGGLE`, reply `OK <new level>`, level before muting remembered by audiod, runtime only). Mute indicator (user request 2026-10-13): muted = `volume_supported` and master 0 %; Home's top bar shows Font Awesome `volume-xmark` left of the Bluetooth headphones / Wi-Fi icons (controllers shift left by its 30 px), the QM volume OSD shows the icon instead of the level and the QM Audio row says "Muted" (812). Checked on the CubeXX panel 2026-10-13.
- System Sound Set v5: `tools/sounds/make-system-sounds.py` (pure Python synthesis, reproducible) writes every cue and the test sound. v4 was rejected as too high: v5 = felt-mallet tones with fundamentals D3–D5, double one-pole low-pass, small room; same loudness as before (peaks −3..−10 dBFS). The chime for ordinary notifications was removed (user: annoying).
- Cues and owners: Navigation Sounds = navigation, select, back, quick-settings, launch (Home starts a game); Notification Sounds (new toggle, `AUDIO_SYSTEM_NOTIFY_ENABLED`, socket `SYSTEM NOTIFY GET|SET`, default On, reset by RESET DEFAULTS) = error (QM toast with severity ≥ warning, Home launch failures) and screenshot (`game.screenshot.saved`); Power Sounds = boot (played by audiod at start), restart, poweroff (QM). `system_sound_allowed()` is the only allowlist.
## Media music, mixer, high resolution (user requests 2026-10-12)
- The Media app's music is the PipeWire stream "nuubOS Music" (nuubos-mediad; streaming-media.md). `93-nuubos-stream-policy.conf` (match on `application.name`) and `nuubos-pw-app-volume` keep it at unity: the Applications volume is the **Game volume** of the Quick Menu mixer and does not scale the music; the **Music volume** is the player's (mediad `VOLUME`). Hardware-checked on the CubeXX: Applications at 50 % left the music stream at 1.00. New streams (fixed 2026-10-15, user: a game started with music on ignored the Game slider until it moved): WirePlumber 0.5 `state-stream.lua` applies `node.stream.default-playback-volume` only with `node.stream.restore-props` on, which the helper turns off, so every new stream started at 100 %; `nuubos-app-volume.lua` (`/usr/share/wireplumber/scripts`, component `custom.nuubos-app-volume` required by `main-embedded` in `90-nuubos.conf`) sets `channelVolumes` = fraction³ on each `node-added` `Stream/Output/Audio` (the cubic scale of `wpctl set-volume N%`, so `wpctl get-volume` shows the slider value). Product streams are recognised by `node.name` `alsa_playback.nuubos-audio-*` (the ALSA plugin sets no `application.process.binary`: the old helper match scaled system sounds and Home Music by the Game volume) or `application.name = "nuubOS Music"`. Checked on the CubeXX: Applications 30 % → new `aplay` stream 0.30, sfx server 1.00.
- `91-nuubos-analog-sink.conf`: the sink is S32LE with `audio.allowed-rates = [44100 48000 96000 192000]` and `default.clock.allowed-rates` the same; no fixed `audio.rate` (it pins the format and the graph never left 48 kHz). The sun4i H616 codec DAI takes S16/S32 at 8–48, 96 and 192 kHz (88.2/176.4 are resampled). The graph switches to a stream's rate when it starts with nothing else running and stays there afterwards (system sounds are resampled meanwhile). Checked: 24/96 FLAC → `hw_params` 96000 S32_LE, 44.1 kHz FLAC → 44100. Not yet qualified: pops at rate switches, a game started while music plays at 44.1/96 kHz, Bluetooth.
- Speaker amplifier park (battery audit 2026-10-14): with the sink idle the PCM stays prepared (SETUP), so DAPM kept the whole analog path on, the speaker amplifier (`Speaker` widget, PA GPIO) included. audiod turns only the codec `Speaker` pin (ALSA `Speaker Switch`) off while `/run/nuubos/screen-off` exists and nothing plays (no `/run/nuubos/media-playing`, no Home Music): the PCM stays open, so no first-cue delay and no reopen pop. Unparked (screen on, Home Music start, any system sound first) the pin follows the jack as the kernel sets it (off with headphones in, patch 0003); a jack event while parked keeps it off. Log: `speaker amplifier parked|back` (audiod stderr). Checked on the CubeXX with a simulated screen-off mark: DAPM `Speaker` Off, back On. Still to check by ear: no pop when the screen comes back on.
- Pops at power transitions (user report 2026-10-22, CubeXX; the speaker amplifier enable is PI5 = `allwinner,pa-gpios` on every H700 board, its supply CLDO1 `vcc-spkr-amp`): (1) Sleep: `pre-power.d/40-audio-park` runs `nuubos-audioctl lifecycle park` (audiod `LIFECYCLE PARK`: the speaker pin goes off synchronously and nothing unparks it, system sounds included) before the kernel powers the codec down; `post-wake.d/40-audio-resume` (new nuubos-system extension point `lifecycle-post-wake`, run by nuubos-systemd after every return from a suspend) sends `LIFECYCLE RESUME` 1 s later in the background, once the codec has settled. (2) Restart/Power Off: nuubos-systemd creates `/run/nuubos/shutting-down` right before `reboot`/`poweroff`; audiod turns the speaker pin off when init stops it (after the shutdown sound); a plain service restart does not. (3) Boot: `nuubos-pipewire-runtime start` turns `Speaker Switch` off when audiod is not running yet, audiod starts assuming it parked and its first reconcile turns it on (codec settled). (4) HyperSleep: the PMIC also switches CLDO1 off (TF-A 0004) and U-Boot SPL drives PI5 low right after the GPIO init (U-Boot 0004). User-confirmed: no pop entering sleep, at restart or power off; a faint one remains at boot and wake (accepted 2026-10-22).
