# System services: lifecycle, System settings, defaults/reset, idle discipline, recovery, jobs, OTA, online

## Lifecycle / power (§20)
Sleep, Restart and Power Off use ONE central lifecycle/power path for every caller (Power OSD and Quick Menu, both in the Quick Menu process; Home; idle timeout; future clients). It owns orchestration (game save-state/pre-power hooks, RGB/display handling (`lifecycle-lighting sleep|wake|shutdown`, platform.md), RTC wake where applicable, final action); the UI only requests.
- §20.1 Automatic save state of an active game before Sleep/Restart/Power Off lives in that central flow, never in UI callers.
- §20.2 Restart/Power Off confirmation: keep the clean centered action visual and show `Press again to confirm` laterally, not under the title.
- §20.3 A Sleep → START/POWER input leak into Settings was fixed/qualified: regressions in wake input suppression/routing are blockers.
- Wake-key guards (fixed 2026-10-11): `nuubos-suspend` writes `/run/nuubos/input/suppress-start` and `suppress-power` before sleeping and keeps each only if its interrupt fired across the sleep (`Key Start`, `axp20x-pek-dbf` in `/proc/interrupts`); `nuubos-inputd` consumes that key's press/release while the marker exists and removes it on the physical release (log `wake-guard ...` in `/run/nuubos/inputd.log`). The START guard never held before: its `case` pattern `''*` matched everything. Waking with power used to open the Power OSD. Both hardware-confirmed on the CubeXX in deep sleep. Restarting inputd over SSH: the init script backgrounds it without `setsid`, so it dies with the session; use `setsid /usr/sbin/nuubos-inputd </dev/null >/dev/null 2>&1 &`.

- Lid (user request 2026-10-11): nuubos-systemd opens the gpio-keys device with `SW_LID` (read-only, not grabbed; inputd ignores it, no mapped keys) and polls it with its other fds. Closing the lid runs the same `enter_sleep()` as Sleep in the Power OSD; opening is the hardware wake (DT wake source). Woken with the lid still closed (a key in a bag), it sleeps again (at most 8 times in a row, stops on `suspend-failed`). Not while HDMI is the active output (docked). STATUS `lifecycle.lid=none|open|closed`, `lifecycle.last_wake=lid` after a lid-open wake. Not hardware-qualified (no SP on the bench; CubeXX shows `none`). Open Lid to Wake (user decision 2026-11-10, Settings → Power row 6 and web, clamshells only, on by default): HyperSleep powers the lid's GPIO bank off, so a lid-close sleep with it on is a quick sleep (`run_suspend(st, by_lid)`, ~3-4 %/h) that the lid opens; Sleep from the power key, the Quick Menu or the timer stays HyperSleep. `LID_WAKE=` in nuubos-system.conf, `SET LID_WAKE 0|1`, STATUS `lid_wake=`. Checked on the CubeXX (no lid: row hidden, setting saved and validated) and in ui-shot `power_lid*`; a real SP still has to try it (community request posted 2026-11-10).

## System Settings (§21)
- Performance Profile: Auto / Performance / Battery Saver; automatic Battery Saver uses a device-global battery threshold.
- Sleep After: value or Off. Screensaver and Power Off After were removed (user decision 2026-10-09/10): systemd config v3 drops `SCREENSAVER_AFTER_MIN`/`POWER_OFF_AFTER_MIN` (old keys ignored), no RTC power-off alarm, no `lifecycle-display`, no Home screensaver; these live in Settings → Power now (ui.md).
- Storage: SD1 + the games card (SD2) and the backup to it, platform.md "SD2 = games card"; never SYSTEM/STATE.
- System Information: reliable live battery/charging, CPU/GPU clock, temperatures, uptime, RAM used/total/free, build, device, network, storage; event-driven where possible, low-frequency sampling only where hardware requires it.
- No generic "Updates & Recovery" category just because it is conventional. Restore Defaults / Reset System Settings with strong confirmation; it never erases ROMs, BIOS, saves or USERDATA and resets controller mapping to the approved default. Before the infrastructure freeze audit all defaults: initial/default/runtime/reset values must agree; no legacy divergent defaults.

## Defaults and Reset System Settings (§37.6)
- Every setting default lives once, in its owning service: `systemd.c` (`DEFAULT_*`: profile Auto, Auto Battery Saver ≤20%, Charge Limit 100 (= off), Screensaver Off, Sleep After 10 min, Hypersleep on, Power Off Off), `audiod.c` (`DEFAULT_*`: output Auto, speaker 70, headphones 50, Bluetooth 50, System Sounds 60, Home Music 60, Applications 100, both cue toggles On), `displayctl.c` (`DEFAULT_BRIGHTNESS` 60), `controllersd.c` (`mapping_defaults`, deadzones 20), `/etc/nuubos/input-bindings.conf`. `S03nuubos-state`/`provision-state.sh` must not write these keys.
- `RESET SYSTEM SETTINGS` (systemd) resets its own config, then calls each owner: `nuubos-audioctl reset-defaults`, `nuubos-displayctl reset`, `nuubos-inputctl bind reset`, D-Bus `org.nuubOS.Controllers1.ResetMappings` (removes `/state/users/*/controllers/*.conf` for ALL users; player assignments kept), `nuubos-sd2-backup reset` (SD2 backup on, every item). Replies `ERR reset incomplete` if any step fails (details in `/run/nuubos/systemd.log`). Not reset: users/login mode, per-user language/rumble/RGB, Wi-Fi/Bluetooth pairings, timezone/time/keyboard, USERDATA.
## Media and idle Sleep (2026-10-12)
- `operation_running()` also holds idle Sleep while `/run/nuubos/media-playing` exists (nuubos-mediad, playing, not paused): music with the screen off or a film has no input for a long time. After a Sleep taken with the Media Screen Off active, systemd runs `nuubos-displayctl screen on`.

## Idle wakeup discipline (§37.9)
- Services must sleep with no timeout when idle; timers are armed only while work is pending (deadline computed, not a fixed tick). Measured 2026-10-05: lightingd/audiod/wifid/bluetoothd/statusd went from ~20 to ~0 wakeups/s.
- Measure on target via `voluntary_ctxt_switches` in `/proc/<pid>/status` over 30 s.
- libdbus `dbus_connection_read_write(conn, ms)` restarts its poll on EINTR: a signal does not wake it. Use own `poll()` on the D-Bus fd + a self-pipe written by the signal handler, then `read_write(conn, 0)`, pop messages, `dbus_connection_flush()` (wifid/bluetoothd pattern). Use `SA_RESTART` and handle `SIGCHLD` the same way instead of periodic `waitpid` (audiod).
- glibc `time()` reads the coarse clock and lags the timerfd by a tick; use `clock_gettime(CLOCK_REALTIME)` for wall-clock display. statusd's minute tick is a `CLOCK_REALTIME` absolute timerfd with `TFD_TIMER_CANCEL_ON_SET`; zone changes come from an inotify watch on `/etc/localtime` + `tzset()`.
- System service supports only `auto`/`battery-saver` (no Performance profile).
- Unsupported rumble/RGB rows are shown as "Unavailable" instead of hidden.

## Background jobs (§37.17, EPIC-007)
- Package `nuubos-jobs`: `nuubos-jobd` (`S39nuubos-jobd`, socket `/run/nuubos/jobd.sock` 0600, log `/run/nuubos/jobd.log`) + `nuubos-jobctl status|watch|submit TYPE [ARG]|run TYPE [ARG]|cancel ID|retry ID` (`run` waits and prints the `@result`; `run --progress` first prints `@progress N` at each change, from jobd's SUBSCRIBE stream, for full-screen progress such as the restore). Host test: `python3 package/nuubos/nuubos-jobs/tests/jobd.py`.
- Job types are registered by the owning package in `/usr/share/nuubos/jobs/<type>.job` (`COMMAND=` absolute program + fixed args, `SCOPE=device|user`, `CANCEL=`, `RETRY=`, `ARGS=0..4`, `NOTIFY=`). Clients only pass validated plain args (no leading `-`, no control chars). Current types: `support-bundle` (nuubos-recovery), `scrape-game`, `scrape-bulk` (nuubos-scraper).
- Workers: nice 10 + idle I/O priority, `NUUBOS_JOB_ID`/`NUUBOS_JOB_USER` env, report `@progress <0..100|-1> [step]`, `@result <text>`, `@error <reason>` on stdout; exit 0 = succeeded; SIGTERM (process group) = cancel, the worker removes partial output. Max 2 running, one per type, FIFO; same type+args pending = same job id. No automatic retry; finished jobs kept in memory (16) for result/retry; nothing persists.
- Every job = Live Notification `id=job.<n> event=job type= state=queued|running|succeeded|failed|cancelled progress= step= reason=` (+ `cancel=1` while running/queued for `CANCEL=1` types: Quick Menu BACKGROUND TASK → Stop) rendered by the Quick Menu (`toast_view` "job").
## OTA updates and product identity (§37.22, EPIC-048)
- `post-build.sh` writes `/etc/os-release` (NAME=nuubOS, VERSION_ID = SemVer from `VERSION` + the image channel `/usr/share/nuubos/release-channel` written by nuubos-update: stable `X.Y.Z`, rc `X.Y.Z-rc.N`, nightly `X.Y.Z-nightly.YYYYMMDD`; a mismatch fails the build; scheme in docs/technical/releasing.md, user request 2026-10-20 "la nightly non può essere sempre 0.5"; BUILD_ID = `git describe`) with `/usr/lib/os-release` linking to it, `/usr/share/nuubos/build-id` and `/usr/share/nuubos/build-serial` (epoch seconds of the image build: the OTA order).
- A/B system slots (user decision 2026-10-12, replaces the in-place file update with `rollback.tar`): slot A = p1 (the flashed image), slot B = p5 (created empty on the first boot, platform.md "Storage"). U-Boot (`board/nuubos/platform/h700/uboot.fragment` CONFIG_BOOTCOMMAND) reads `nuubos-slot.cfg` on NUUBOS_BOOT (p2): `nuubos_slot` (good slot), `nuubos_try` (slot on trial or `none`), `nuubos_tries`; a trial boot spends one try and writes the file back (`fatwrite`; a failed write boots the good slot); with no tries left it boots the good slot; a slot that cannot be loaded falls through to the good slot, then A, then `distro_bootcmd`. extlinux.conf takes `root=${nuubos_root} nuubos.slot=${nuubos_boot}` from U-Boot (pxe expands `${}` in APPEND) and `panic=10` (a panicking kernel restarts and spends a try). A soft or hard lockup of a CPU panics (lockup detectors, platform.md) and so restarts too; a hang of the whole SoC is reset by the hardware watchdog after 16 s (`S12nuubos-watchdog`, stopped across sleep by `nuubos-suspend`; platform.md). U-Boot/SPL/TF-A are updated by OTA since 2026-10-22 (user request: "OTA must update EVERYTHING"; before, an updated console kept the bootloader it was flashed with): `post-build.sh` ships `u-boot-sunxi-with-spl.bin` in `/usr/share/nuubos/bootloader/`, and `nuubos-update-apply confirm` (every nuubUI ready) writes it to SD1 at 8 KiB when the card holds another one, only from a slot that reached nuubUI, battery above 20 % (`MIN_BATTERY_BOOTLOADER`, 2026-10-23: the install needs above 30 %, the margin keeps a console that started just above it from postponing the write; else at a later boot), read back (BLKFLSBUF) and written again once on a mismatch; `/state/update/bootloader` = SHA-256 last verified. No fallback copy: the H616 BROM's backup location (256 KiB) overlaps the 745 KiB primary below p1 (1 MiB), so a power loss during the ~1 s write needs an SD reflash. Host test covers it (`NUUBOS_TEST_DISK`).
- Package `nuubos-update`: `nuubos-updatectl status|channel [stable|rc|nightly]|check|download|verify|write DEVICE` (libcurl + libsodium + zlib). GitHub Releases: `<UPDATE_URL>/channel-<channel>/nuubos-update.manifest(.sig)` (UPDATE_URL = `https://github.com/baf93/nuubOS/releases/download`); manifest format=2 key=value: channel, version, serial, build, payload (`<tag>/<file>`, its versioned release), size, sha256 (of the payload), image_size, image_sha256 (of the system image), notes; signed Ed25519, public key compiled from `board/nuubos/common/ota/update-key.pub` (64 hex; absent → "unavailable"). Offered only when the signature verifies, the format is 2, its channel is the device's or a more stable one and its serial is above the running one (an old signed manifest never downgrades). Since 2026-10-22 (user request) `check` reads the device's channel and every more stable one (nightly: nightly, rc, stable; rc: rc, stable; stable: stable) and keeps the newest verified manifest by serial; installing it never changes the device's channel; a signature/HTTP failure on one channel does not hide an update found on another (the error is reported only when nothing newer was found). A manifest whose `channel=` differs from the release it is published under is ignored. Channels (user decision 2026-10-14: Nightly · RC · Stable): `nightly` (was `alpha`), `rc` (was `beta`), `stable`; labels "Nightly", "RC", "Stable" in every language (987/988/986). Channel in `/state/update/channel` (an old `alpha`/`beta` there reads as `nightly`/`rc`; nothing had been published on the old channels), default `NUUBOS_UPDATE_DEFAULT_CHANNEL` (.mk: the channel the image is published on, user decision 2026-10-16 — nightly during Alpha, an RC/stable image is built with `NUUBOS_UPDATE_DEFAULT_CHANNEL=rc|stable` on the compile.sh command line; stable on 2026-10-15); changing it forgets the downloaded manifest/payload. `check`: `OK available V` | `OK current` | `OK none` (404: nothing published on the channel, e.g. no release yet: "Up to date", 2026-10-12 — before, any non-200 was reported as a network error) | `ERR network` (no HTTP answer) | `ERR server` (HTTP error such as a GitHub rate limit or 5xx: 1013) | `ERR signature`. Resumable payload download (explicit Range; a 200 answer restarts; free-space check → `space`), SHA-256 verified, `.part` deleted when wrong; files in `/userdata/.nuubos-update`. `write` re-verifies the payload, gunzips it onto the slot device checking image size + SHA-256, fsyncs, drops the cache (BLKFLSBUF) and reads the slot back against image_sha256. Job types `update-download`, `update-install`. One updater at a time (2026-10-25): `check`, `download` and `write` take `flock(LOCK_EX|LOCK_NB)` on `/run/nuubos-update.lock` (`UPDATE_LOCK`) and answer `ERR busy` otherwise (`status`, `channel`, `auto` do not lock). Found on the CubeXX: a manual `updatectl download` started 11 s before the Settings job, both appended to `payload.part`, which grew to 457,231,574 bytes for a 434,793,686-byte payload and failed `checksum` at 100 % (UI: notification "Downloading update · Failed", Settings "The update could not be verified"). jobd already runs one `update-download` per argument set, so a single UI download is not affected.
- Download sources (RC5, user decisions 2026-11-10): SourceForge is the backend of every channel (`UPDATE_SOURCES` = `https://downloads.sourceforge.net/project/nuubos`, which redirects to a signed `master.dl.sourceforge.net` URL, honours Range, 404 for a missing file); GitHub Releases (`UPDATE_URL`) carry stable releases only and are the fallback, asked only when no other source answers at all (a 404 or a bad signature counts as an answer), so consoles do not poll GitHub. Every check asks all the non-fallback sources and keeps the newest verified manifest; the payload is fetched from them in order, GitHub last. A verified manifest may carry `sources=` (up to 4 https base URLs), saved to `/state/update/sources`, which replaces `UPDATE_SOURCES` (a manifest without it goes back to the compiled list); only a signed manifest changes it. Consequence: from RC5 on, every release must be on SourceForge before (or with) its channel manifest, or RC5+ consoles see nothing (they do not fall back on a 404). Publishing: `tools/ota/publish-sf.sh` (rsync over SSH, `NUUBOS_SF_USER`), `tools/ota/publish.sh` refuses non-stable channels unless `NUUBOS_GITHUB_PRERELEASE=1` (once, for RC5). Host test: `sh package/nuubos/nuubos-update/tests/sources.sh` (three local hosts, a throw-away key, 12 cases).
- `nuubos-update-apply install [restart]|apply|boot|confirm|status`: `install` (job `update-install` = `install restart`) writes the inactive slot via `updatectl write` (never the running one, never a mounted one), copies per-device files kept on the system slot (`etc/nuubos/splash.palette`), marks it pending and restarts after the job reported success. The pre-power hook `90-update` (restart/poweroff, never sleep) sets `/state/update/trying`, copies STATE to `/var/lib/nuubos-update/state.tar` on the running slot and writes `nuubos-slot.cfg` (good = running, try = new, tries = 3). On the new slot Home confirms once nuubUI is ready (not in safe mode): good = new, try = none, payload deleted. S03 (`boot`, right after STATE is mounted, before anything reads it): `trying` set but the running slot is the old one → U-Boot gave up: STATE gets its copy back (a `restoring` marker makes a restore cut by a power loss finish at the next boot), result `rolled-back` (Home and the web page say "The previous version was restored"). Status `slot= pending= trying= result=` (trying|ok|rolled-back|failed).
- Release key (user decision 2026-10-12): no key file anywhere. `tools/ota/release-key.py new` makes a random passphrase (25 Crockford base32 characters = 125 bits, shown once, kept in the maintainer's password manager) and writes `update-key.pub`; the Ed25519 seed = scrypt(passphrase, salt "nuubOS release key v1", N=2^17, r=8, p=1), derived in memory at each signature and handed to openssl through a pipe; `check` / `sign` refuse a passphrase that does not match `update-key.pub`. Never change the KDF parameters (every device trusts the derived key). Losing the passphrase = devices need a reflash to trust a new key.
- Releases (tools/ota): `make-update.sh OUTDIR CHANNEL [NOTES_URL]` (asks the passphrase once, checks it before compressing) from `output/h700/images/rootfs.ext4` (payload = its gzip) and `rootfs.tar` (serial, build id), tag `v<version>` (version read from the image's os-release; make-update refuses a channel mismatch or a `-dirty` build); `publish.sh OUTDIR` (GitHub CLI `gh`, push the commit first) creates the versioned release with the payload (pre-release unless stable), then replaces the manifest + signature of the fixed release `channel-<channel>` (a pre-release, never "Latest"; created on first use). ## Automatic time (2026-10-10)
- Sync used to run only on a Wi-Fi connection (wifi event → `nuubos-status-time-sync`, skipped when the last sync is < 6 h old), so a console that stayed connected drifted (user report). statusd now runs the helper once an hour from its minute timer while Wi-Fi is connected (`maybe_time_sync`, double fork); the helper still syncs only with Automatic Time on and a last sync ≥ 6 h old.
- Automatic syncs go through regionald (2026-10-22, was an open item): `nuubos-status-time-sync` asks `nuubos-regionalctl sync` (SYNC_NOW), so regionald records the sync and notifies its subscribers (Settings -> Last Sync was stale until the next regionald command); `nuubos-timectl sync` directly only when regionald does not answer (log `via=regionald reply=...`).
- Restart / Power Off order (user report 2026-10-22: closing animation, then a black lit screen, then the splash, then the real power off): nuubos-systemd now runs lighting + UI splash (`notify_ui_lifecycle`) first and the pre-power hooks (game save/close, update install, diagnostic report) under the splash, then 0.5 s and reboot/poweroff.
- Black screen before the splash (fixed 2026-10-28; measured on the CubeXX with a loop reading `/sys/kernel/debug/dri/0/state` + `framebuffer` and `/dev/fb0` into /userdata during a real Restart, no DRM fd opened): Home's final splash stayed until `nuubos-lifecycle-finalize` killed labwc, then the active plane had `fb=0` (black, backlight on) for the whole of rcK (7+ s), and the fbdev splash `--prepare` had drawn only appeared at the device's last close, ~1 s before the power cut. A DRM client's framebuffers are removed when it exits and the kernel turns off the planes showing them: `nuubos-splash --hold` (an open fd) keeps fbdev from being restored but cannot keep labwc's frame. Now finalize runs `nuubos-splash --handoff MODE` before the kill: it renders the same final raster into its own dumb buffers per connected output (each at its own mode, like the boot `--kms` splash), a child polls `drmSetMaster` (1 ms) and sets the CRTCs the moment labwc is gone, touches `/run/nuubos/handoff-shown` (finalize logs `drm-handoff=shown`) and holds the device until init kills it; then fbdev shows the identical prepared raster. `--hold` stays as the fallback when the preparation fails; the child exits when it never gets master (restart abandoned). Still a micro flash after that (user, same day): the kernel turned the plane off at labwc's exit before the child could take master (one black frame). labwc patch 0007: SIGUSR2 drops DRM master (`DRM_IOCTL_DROP_MASTER` on `wlr_backend_get_drm_fd`) and leaves the scanout untouched; finalize sends it after `--handoff` is prepared, the child swaps its buffer onto the same primary plane in one commit (`drm-handoff=shown-before-kill`), and only then labwc is killed (its buffers are no longer on screen, nothing is turned off). Checked on the CubeXX: plane 41 labwc fb -> nuubos-splash fb with labwc still alive, unchanged after the kill.
- Online sync (user request 2026-10-10): `nuubos-status-time-sync online` runs on the wpa_cli `CONNECTED` event (exact match: `*CONNECTED*` also matched DISCONNECTED) and at S48 start (boot); it waits up to 30 s for a default route AND a resolving `pool.ntp.org` (right after CONNECTED the old route is still there and DNS fails), then syncs unless the last sync is < 10 min old. Never with Automatic Time off (a manual date/time requires it off). `nuubos-timectl sync` refuses without DNS (BusyBox `ntpd -q` exits 0 when no server name resolves: it was recorded as a sync) and kills ntpd after 12 s (it retries forever; no `timeout(1)` on the target; inside the UI's 15 s Sync Now timeout). Log `/run/nuubos/status-time-sync.log` (`mode=online|periodic`).
